# Full-product QA audit — 2026-09-02

## Scope and method

This pass reviewed the Django models, migrations, serializers, permissions,
queryset scoping, APIs, automated tests, and the React application from login
through administration, academics, students, classes, attendance, assessments,
performance, dashboard, settings, and reports.

The API was exercised through the complete pytest suite and strict OpenAPI
generation. The UI was reviewed statically and validated with TypeScript,
ESLint, Prettier, and a production build. This environment does not provide a
browser runner or seeded end-to-end test account, so visual, keyboard, mobile,
and real-network timing checks still require the manual release checklist.

## Issues found and corrected

1. **Critical — queued API requests never completed after refresh failure.**
   Concurrent requests waiting for a new access token were only notified on
   success. A failed refresh logged the user out but left every queued promise
   pending, producing permanent loading states. The queue now rejects and
   clears on failure.

2. **High — recorded academic history could be physically deleted.**
   Core attendance, marks, submissions, ratings, enrollment, allocation, and
   semester relationships used cascading foreign keys. A direct ORM or Django
   admin deletion could erase history despite API soft-archive rules. These
   relationships now use `PROTECT`, with migrations and regression coverage.

3. **High — attendance/marks/submission editors could overwrite late data.**
   The UI enabled editing before existing records finished loading. A fast user
   could enter values that were then replaced by the response, or save from an
   incomplete initial state. Controls and saves now wait for both roster and
   existing-record requests and expose retryable errors.

4. **High — inactive entities could receive new academic relationships.**
   Several create and bulk APIs accepted inactive students, batches, programs,
   semesters, classes, subjects, or teacher accounts. Serializer validation now
   blocks those writes while preserving read access to historical records.

5. **High — clearing a student's email left the linked login identity stale.**
   Student PATCH only copied a non-empty email to the managed user. Clearing it
   created inconsistent student and account records. Both identities now stay
   synchronized, with history attribution tested.

6. **Medium — older attendance silently disappeared from UI workflows.**
   Attendance history and “copy previous” loaded only the first 200 sessions.
   Both requests now explicitly fetch the full authorized history.

7. **Medium — performance settings failed open.**
   When the settings request failed, default values remained saveable and could
   overwrite the real configuration. Save is now blocked on load error and a
   clear retry action is shown.

8. **Medium — assignment dates used UTC instead of the user's local date.**
   Around midnight, a new assignment could default to yesterday or tomorrow.
   The form now uses the shared local-date helper.

9. **Medium — documented import and tenant-resolution endpoints broke strict
   schema generation.** Import upload/result and tenant-resolution serializers
   are now explicit. Strict OpenAPI validation completes without warnings.

10. **Low — noisy security/deprecation warnings obscured test failures.** The
    JSON logger import path was updated, tests now use an explicit strong key,
    and non-debug deployments reject secrets shorter than 32 characters.

## Residual risks and release decisions

1. **High QA gap — no automated browser tests.** There are no Playwright,
   Cypress, or component tests. Add smoke coverage for each role, route guards,
   attendance entry, marks Enter navigation, bulk save errors, dark mode,
   mobile tables, and session expiry before treating UI regressions as gated.

2. **Medium — attendance accepts partial rosters by current policy.** The API
   intentionally permits saving a subset of enrolled students, while some UI
   language implies the whole roster is recorded. Product should either label
   partial sessions clearly or require one record per active enrollment.

3. **Medium — email uniqueness is case-sensitive at the database layer.** API
   validation/login are case-insensitive, but direct or concurrent writes could
   create case variants. A functional unique constraint on normalized email is
   recommended after a production duplicate audit.

4. **Medium privacy review — production error monitoring sends default PII.**
   Confirm this matches the institution's privacy policy and data-processing
   agreement before release; disable it if not explicitly required.

5. **Deployment warning — local migration state is not representative.** The
   configured local database reports the full tenant migration chain pending.
   Do not apply migrations to production from this workstation. Back up, audit
   tenant migration state, and apply the three new `PROTECT` migrations through
   the reviewed deployment process.

6. **Operational warning — the virtualenv's `pytest` launcher has a stale
   absolute shebang.** `venv/bin/python -m pytest` works and was used. Recreate
   the virtualenv when convenient.
